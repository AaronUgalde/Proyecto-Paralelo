\section{Marco teórico}
\label{sec:cap05:marco}

El cómputo paralelo de memoria distribuida organiza la ejecución en procesos independientes, cada uno con su propio espacio de direcciones, que cooperan intercambiando mensajes de forma explícita. \textit{Message Passing Interface} (MPI) es la especificación estándar de ese modelo, definida por el MPI Forum \cite{mpiforum2021}, y \textbf{Open MPI} es una de sus implementaciones de código abierto, de uso muy extendido en equipos de escritorio y en clústeres \cite{openmpi2024}. En lenguaje C, la interfaz se obtiene con la cabecera \texttt{<mpi.h>} \cite{pacheco2011}.

A diferencia de los hilos del capítulo anterior, que comparten memoria dentro de un mismo proceso, en MPI los datos sólo viajan si el programador los envía o los recolecta con una llamada. Un programa MPI es un único ejecutable que el lanzador (\texttt{mpirun}) copia en $P$ procesos; cada copia se distingue por su \textit{rank}, un entero entre $0$ y $P-1$ dentro de un \textit{comunicador}. Las funciones usadas en este capítulo son:
\begin{itemize}
    \item \texttt{MPI\_Init()} y \texttt{MPI\_Finalize()}: inician y cierran el entorno MPI.
    \item \texttt{MPI\_Comm\_rank()} y \texttt{MPI\_Comm\_size()}: devuelven el identificador del proceso y el total de procesos del comunicador \texttt{MPI\_COMM\_WORLD}.
    \item \texttt{MPI\_Gatherv()}: operación colectiva que reúne en un proceso raíz bloques de tamaño distinto enviados por cada proceso.
    \item \texttt{MPI\_Reduce()}: operación colectiva que combina un valor de cada proceso en el proceso raíz (aquí, la suma de los aportes a cada $S_N(x)$ y el máximo del tiempo de ejecución).
    \item \texttt{MPI\_Wtime()}: reloj de pared para medir tiempos.
    \item \texttt{MPI\_Abort()}: termina todos los procesos ante un error irrecuperable.
\end{itemize}

La compilación se hace con el envoltorio \texttt{mpicc}, que invoca al compilador de C del sistema (en macOS, Apple Clang) con las rutas y bibliotecas de MPI, y la ejecución con \texttt{mpirun -np P}. Cuando se piden más procesos que núcleos disponibles se agrega \texttt{--oversubscribe}, que permite al sistema operativo planificarlos por turnos.

\section{Programación con openMPI en lenguaje C y en la plataforma macOS}
\label{sec:cap05:programacion}

Se programaron en C los coeficientes de la serie de Fourier de la misma función del Capítulo 4, $f(x) = -\frac{1}{4}x^4 + 3$, para los primeros $100$ armónicos. Al ser $f$ una función par, $b_n = 0$ y
\[
a_n = \frac{2\,(-1)^n\,\left(6 - n^2\pi^2\right)}{n^4},
\qquad
\frac{a_0}{2} = 3 - \frac{\pi^4}{20} \approx -1.8704546 .
\]
Se ejecutan $100$ procesos MPI, uno por armónico, y el código también funciona con cualquier $P$ entre $1$ y $100$. Además de los coeficientes, el programa evalúa la serie en $201$ puntos $x\in[-\pi,\pi]$ para poder graficar la función original y sus sumas parciales
\[
S_N(x) = \frac{a_0}{2} + \sum_{n=1}^{N}\left(a_n\cos nx + b_n\sin nx\right),
\qquad N \in \{1,3,5,10,50,100\}.
\]

\subsection{Fragmentos de código explicados}

\textbf{Función de cálculo.} Es la misma fórmula de $a_n$ y $b_n$ que usó cada hilo en el Capítulo 4; sólo cambia quién la ejecuta:

\begin{lstlisting}[style=C]
static void calcular_armonico(int n, double *an, double *bn)
{
    *an = (2.0 * ((n % 2 == 0) ? 1.0 : -1.0) *
          (6.0 - (n * n * M_PI * M_PI))) /
          ((double)n * n * n * n);
    *bn = 0.0; /* la funcion es par */
}
\end{lstlisting}

\textbf{Inicio, validación y reparto.} Tras \texttt{MPI\_Init}, cada proceso consulta su \texttt{rank} y el total \texttt{size}. Se valida que no haya más procesos que armónicos y se reparte el trabajo por bloques: los primeros \texttt{resto} procesos reciben un armónico adicional cuando $100$ no es divisible entre $P$.

\begin{lstlisting}[style=C]
MPI_Init(&argc, &argv);
MPI_Comm_rank(MPI_COMM_WORLD, &rank);
MPI_Comm_size(MPI_COMM_WORLD, &size);

if (size > NUM_ARMONICOS) { /* error y salida limpia */ }

int base   = NUM_ARMONICOS / size;
int resto  = NUM_ARMONICOS % size;
int mios   = base + (rank < resto ? 1 : 0);
int inicio = rank * base + (rank < resto ? rank : resto);
\end{lstlisting}

\textbf{Cálculo local.} Cada proceso llena un arreglo propio con tres valores por armónico ($n$, $a_n$, $b_n$). No hay memoria compartida: el resultado vive en la memoria privada del proceso hasta que se recolecta.

\begin{lstlisting}[style=C]
for (int i = 0; i < mios; i++) {
    int n = inicio + i + 1;          /* armonicos 1..100 */
    double an, bn;
    calcular_armonico(n, &an, &bn);
    local[i*CAMPOS + 0] = n;
    local[i*CAMPOS + 1] = an;
    local[i*CAMPOS + 2] = bn;
}
\end{lstlisting}

\textbf{Aporte a la gráfica.} Dentro del mismo ciclo, cada proceso suma el término $a_n\cos nx + b_n\sin nx$ de su armónico en un arreglo local \texttt{aporte}, para cada suma parcial $S_N$ con $n\le N$ y para cada punto $x$. Así, el cálculo de la gráfica también se reparte entre los procesos.

\begin{lstlisting}[style=C]
for (int c = 0; c < NUM_CORTES; c++) {
    if (n > CORTES[c]) continue;
    for (int k = 0; k < NUM_PUNTOS; k++) {
        double x = -M_PI + 2.0*M_PI*k/(NUM_PUNTOS-1);
        aporte[c*NUM_PUNTOS + k] += an*cos(n*x) + bn*sin(n*x);
    }
}
\end{lstlisting}

\textbf{Recolección.} El proceso $0$ calcula cuántos datos envía cada proceso (\texttt{conteos}) y en qué posición del arreglo final se colocan (\texttt{desplaz}); \texttt{MPI\_Gatherv} reúne todos los coeficientes en una sola llamada; \texttt{MPI\_Reduce} con \texttt{MPI\_SUM} suma los aportes de todos los procesos para formar cada $S_N(x)$, y otro \texttt{MPI\_Reduce} con \texttt{MPI\_MAX} obtiene el tiempo del proceso más lento. Esta operación colectiva sustituye al \texttt{pthread\_join()} del capítulo anterior y a los semáforos de la fase de procesos: cada proceso escribe sólo en su propio bloque, por lo que no hay condiciones de carrera.

\begin{lstlisting}[style=C]
MPI_Gatherv(local, mios * CAMPOS, MPI_DOUBLE,
            todos, conteos, desplaz, MPI_DOUBLE,
            0, MPI_COMM_WORLD);

MPI_Reduce(aporte, suma, NUM_CORTES * NUM_PUNTOS,
           MPI_DOUBLE, MPI_SUM, 0, MPI_COMM_WORLD);

MPI_Reduce(&t_local, &t_max, 1, MPI_DOUBLE,
           MPI_MAX, 0, MPI_COMM_WORLD);
\end{lstlisting}

{\emergencystretch=3em Finalmente el proceso $0$ suma $a_0/2$ a cada $S_N(x)$ y escribe dos archivos para importar a Excel: \texttt{fourier\_\allowbreak mpi\_\allowbreak resultados.csv} (columnas \texttt{n}, \texttt{an}, \texttt{bn} y \texttt{proceso}), cuya primera fila ($n=0$) guarda el término constante $a_0/2$ y \texttt{fourier\_\allowbreak mpi\_\allowbreak grafica.csv} (columnas \texttt{x}, \texttt{f\_\allowbreak original}, \texttt{S\_\allowbreak 1}, \texttt{S\_\allowbreak 3}, \texttt{S\_\allowbreak 5}, \texttt{S\_\allowbreak 10}, \texttt{S\_\allowbreak 50} y \texttt{S\_\allowbreak 100}). El código completo y el \texttt{Makefile} están en los anexos (sección~\ref{sec:cap05:anexos}).\par}

\subsection{Comparación con las fases anteriores}

\begin{enumerate}
    \item \textbf{Precisión numérica:} los coeficientes $a_n$ y $b_n$ calculados con openMPI usan la misma fórmula del Capítulo 4 y coinciden con los de los hilos y con el desarrollo analítico del Capítulo 1; cambiar de modelo de programación no altera el resultado matemático, y éste tampoco depende del número de procesos.
    \item \textbf{Modelo de memoria:} en la fase de procesos con \texttt{fork()} (memoria compartida y semáforos) y en la de hilos (con \texttt{pthread\_join()}) los ejecutores compartían memoria y había que sincronizarlos; en MPI cada proceso tiene memoria privada y la información se reúne con una operación colectiva, que además es la base para ejecutar en varias máquinas.
    \item \textbf{Costo de ejecución:} el cálculo de cada armónico es muy corto, por lo que en este problema el tiempo lo domina el costo de lanzar y coordinar los procesos y no la aritmética. Con un único proceso el cálculo tarda microsegundos, mientras que con $100$ procesos (más que núcleos disponibles) tarda unos milisegundos. Para esta carga el paralelismo no acelera el cálculo, pero sí ilustra el modelo y escalaría con problemas más pesados.
\end{enumerate}

\subsection*{Análisis del lenguaje y la técnica utilizada}
Se usó lenguaje C por su cercanía con el sistema operativo y porque MPI define su interfaz principal en C. La técnica es paralelismo de datos: el dominio (los $100$ armónicos) se divide entre procesos que ejecutan el mismo programa sobre distintos datos (modelo SPMD). Al no compartir memoria, no hacen falta semáforos ni \textit{mutex}; la única comunicación es la recolección final en el proceso $0$.

Descargar la información generada por los procesos de OpenMPI a un archivo estructurado para luego volcarla en nuestra plantilla de Excel fue fundamental para corroborar empíricamente nuestra lógica. Al observar que las nuevas gráficas coincidían perfectamente con las curvas generadas en los capítulos previos, comprobé que la paralelización distribuida no alteró la precisión matemática de la serie. Mantener un control estricto sobre el flujo de los datos me enseñó que la eficiencia no debe comprometer la exactitud en los cálculos al momento de ensamblar las sumatorias.

Asimismo, el análisis de la implementación me hizo mucho más consciente del impacto directo que tiene el hardware subyacente en el rendimiento del código. Al realizar las pruebas y ejecuciones desde mi entorno macOS, documentando cómo los procesos interactuaban con los núcleos del procesador Apple M5 y los 16 GB de memoria de mi equipo, logré dimensionar el verdadero costo de la latencia en las comunicaciones y el papel de la memoria caché. Sumado a esto, organizar el proyecto mediante el archivo \texttt{Makefile} y asegurar una compilación impecable mediante \texttt{mpicc} sin advertencias fue esencial; en un entorno de paso de mensajes, cualquier ambigüedad en el código C puede derivar en bloqueos que son sumamente complejos de depurar.

En conclusión, esta fase del proyecto me demostró que el cómputo paralelo requiere una sinergia perfecta entre el conocimiento matemático, la arquitectura del software y las características del equipo de cómputo. Dividir la carga computacional de la serie de Fourier en fragmentos manejables por OpenMPI me brindó una perspectiva invaluable para mi formación analítica. Comprender cómo escalar cálculos complejos de manera distribuida es una competencia técnica fundamental que, sin duda, será clave para futuros desarrollos donde la complejidad algorítmica exija superar las limitaciones del procesamiento secuencial tradicional.

\subsection*{Conclusión Ugalde Téllez}
% Redactada por Claude (2026-10-22) con base en el código real; Aarón puede ajustarla.

Esta fase me hizo cambiar la forma de pensar el mismo problema. En los capítulos anteriores la serie de Fourier se calculó con procesos creados con \texttt{fork()} y con hilos, y en los dos casos había memoria que compartir y algo que sincronizar. Con openMPI esa idea desaparece: cada proceso tiene su propia memoria, calcula su armónico y lo único que existe es la comunicación explícita. Entender que ya no podía escribir en un arreglo común, sino que tenía que recolectar los resultados con \texttt{MPI\_Gatherv}, fue lo más formativo del capítulo.

Programar el reparto también tuvo su detalle. Con $100$ procesos cada uno toma un armónico, pero quise que el programa funcionara con cualquier número de procesos entre $1$ y $100$, así que calculé bloques desiguales con \texttt{base} y \texttt{resto}, y los tamaños y desplazamientos que necesita \texttt{MPI\_Gatherv}. Probé el programa con $1$, $7$ y $100$ procesos y los coeficientes y el archivo de la gráfica salieron idénticos en los tres casos (sólo cambia la columna \texttt{proceso}), lo cual me dio confianza de que el reparto estaba bien. También agregué una validación para rechazar más de $100$ procesos, porque en un programa paralelo un dato fuera de rango puede dejar procesos esperando para siempre.

Una observación que no esperaba es que usar $100$ procesos tardó unos milisegundos, mientras que con un solo proceso el cálculo duró microsegundos. Cada armónico es una operación tan pequeña que el costo de lanzar y coordinar los procesos pesa más que el cálculo, y como el equipo tiene menos núcleos que procesos tuve que usar \texttt{--oversubscribe}. Aprendí que paralelizar no siempre acelera: depende de que el trabajo de cada proceso sea lo bastante grande frente al costo de comunicarlos.

También valoré el trabajo con \texttt{Makefile}: compilar con \texttt{-Wall -Wextra} y lograr cero advertencias me obligó a revisar tipos y conversiones, y poder lanzar todo con \texttt{make run} hizo las pruebas repetibles. Llevar los datos del CSV a Excel y ver que las gráficas coincidían con las fases anteriores confirmó que el modelo de programación cambia la forma de ejecutar, pero no el resultado matemático. Me llevo de esta fase una base sólida para entender cómo se trabaja en memoria distribuida, que es el paso natural para ejecutar programas en varias máquinas.
